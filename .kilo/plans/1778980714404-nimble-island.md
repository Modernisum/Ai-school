# OCR + LLM Auto-Fill & Dynamic Form System — Implementation Log

## Overview

Transform Vidhyam from manual *Data Entry* to **Data Verification**. Admin uploads a document (Aadhaar, PAN, TC, Marksheet) → OCR extracts text → LLM parses into structured fields → form is 70-80% pre-filled → Admin reviews/assigns remaining fields → Submits.

**Status: IMPLEMENTED** (2026-05-17)

---

## Phase 1: Backend OCR + LLM Service ✅

### 1.1 New File: `Backend/src/services/ocr_service.rs` ✅

`OcrService` struct with:
- `registry: Arc<ProviderRegistry>` — to resolve the school's AI provider
- `http_client: reqwest::Client` — shared HTTP client (reused across requests)

**Methods:**
- `extract_from_document(school_id, file_url, doc_type)` — main extraction method. Routes to Gemini Vision (direct API call) if provider is `google_gemini`, otherwise falls back to text-based LLM extraction.
- `extract_batch(school_id, docs)` — batch extraction, merges fields from multiple documents
- `call_gemini_vision(prompt, file_url)` — direct call to Gemini 1.5 Pro with `file_data` support (the existing `GoogleGeminiProvider` `generate_text` method doesn't support vision inputs)

**Key implementation details:**
- Uses `GEMINI_API_KEY` env var for Gemini Vision calls (separate from the DB-configured provider API key because the DB provider stores the key for the text interface, not the vision endpoint)
- Non-Gemini providers use the standard `generate_text` interface with a text prompt describing the document
- Response is parsed from LLM JSON output, with markdown fence stripping
- The `reqwest::Client` is a shared field on the struct, not created per-call

### 1.2 New File: `Backend/src/routes/ocr.rs` ✅

**Endpoints:**
```
POST /api/school/:schoolId/ocr/extract
  Body: { fileUrl: string, docType: string }
  Response: { success: true, data: { docType, extractedFields: {...}, rawLength } }

POST /api/school/:schoolId/ocr/extract-batch
  Body: { files: [{ fileUrl, docType }] }
  Response: { success: true, data: { mergedFields: {...}, documents: [...] } }
```

### 1.3 New File: `Backend/src/domain/ocr.rs` ✅

Routes registered under `/school/:schoolId/ocr` in the main router.

### 1.4 OCR Engine ✅

Only Gemini Vision mode implemented via direct HTTP call to `gemini-1.5-pro:generateContent` with `file_data` part. Non-Gemini providers use text-only prompt.

### 1.5 New Migration: `Backend/migrations/202605170000_ocr_extractions.sql` ✅

```sql
CREATE TABLE IF NOT EXISTS ocr_extractions (
    id SERIAL PRIMARY KEY,
    school_id VARCHAR(255) NOT NULL,
    doc_type VARCHAR(50) NOT NULL,
    file_url TEXT NOT NULL,
    raw_text TEXT,
    extracted_fields JSONB NOT NULL DEFAULT '{}',
    entity_type VARCHAR(20),
    entity_id VARCHAR(255),
    created_at TIMESTAMP WITH TIME ZONE DEFAULT CURRENT_TIMESTAMP
);
```

**Note:** The `extracted_fields` type was changed from `HashMap<String, String>` to `serde_json::Value` in the actual implementation, since the output is returned as JSON directly from the LLM response.

## Key Technical Decisions (As Implemented)

1. **OCR Engine**: Direct call to `gemini-1.5-pro:generateContent` with `file_data` part, using `GEMINI_API_KEY` env var. The existing `GoogleGeminiProvider`'s `generate_text` method was not suitable because it only supports text parts — the vision file attachment needs to go in `contents[].parts[]` not in `generationConfig`.

2. **Provider Fallback**: For non-Gemini providers, the system sends a text-only prompt to the provider's `generate_text`. This won't work for vision documents but provides basic structured extraction from form text data.

3. **Document Upload**: Uses the existing `/api/storage/upload` endpoint which handles multipart upload with MIME validation, duplicate detection, and tenant isolation. Returns a public URL that is then passed to the OCR service.

4. **No new DB columns**: All new fields (blood group, medical history, bank details, etc.) go into existing JSONB columns. No migration needed for new fields.

5. **Error handling**: If OCR or LLM fails, the form is still fully usable manually via "Skip & Fill Manually".
